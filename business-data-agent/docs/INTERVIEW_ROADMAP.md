# Agent 面试准备路线

这份路线只梳理 Agent 项目，不混入 RAG 项目的实现细节。目标是先把 Agent 做到能运行、能讲、能改、能写进简历；等 Agent 验收完成后，再回到 RAG 项目做真实演示和评测，最后再做融合。

## 1. 当前先做 Agent

Agent 项目当前优先级不是继续堆功能，而是把演示闭环和工程边界讲清楚。

面试前需要确认：
- `python scripts/smoke_demo.py` 可以稳定跑通注册、登录、创建数据源、自然语言分析和报告导出。
- `pytest` 可以通过。
- `python evals/run_agent_eval.py --json` 可以输出稳定通过的评测结果。
- Swagger 可以完成登录、创建数据源、提问，并展示 `answer`、`sql_query`、`data`、`tool_trace`。
- 能解释 SQL 只读限制、危险 SQL 拦截、最大工具调用步数、工具结果压缩和兜底回答。

## 2. Agent 演示顺序

推荐现场演示顺序：
1. 先运行 `python scripts/smoke_demo.py`，证明项目不依赖外部模型也能跑通后端链路。
2. 再运行 `python evals/run_agent_eval.py --json`，证明不是只靠一次手工演示。
3. 打开 Swagger，演示注册、登录、创建数据源和提问。
4. 展示一次 `tool_trace`，说明 Agent 先读取 schema，再执行只读 SQL，最后保存结果。
5. 展示报告导出，说明结果可以沉淀和复核。

推荐问题：
- `2024 年每月收入趋势如何？`
- `各产品线毛利率是多少？`

## 3. 真实模型分支怎么讲

如果配置了 `API_KEY`，项目会走真实 Function Calling 分支。真实模型可能会多次调用 `get_schema`、`preview_table`、`execute_sql` 等工具。

这里要重点讲两个工程控制：
- 最大工具步数：`MAX_AGENT_STEPS` 防止 Agent 无限循环。
- 兜底回答：如果模型在最大步数内没有生成最终总结，但 SQL 已经查到数据，系统会基于已有结果返回阶段性分析，而不是直接报“分析步骤过多”。

面试表达可以这样说：

> 我没有简单把最大步数无限调大，而是做了两层控制：一是压缩工具结果，减少模型被长 schema 或预览数据带偏；二是在达到最大步数时，如果 SQL 已经执行成功，就基于结构化结果返回可复核的兜底分析。

## 4. 什么时候回到 RAG

Agent 项目满足下面条件后，就可以暂停 Agent，回到 RAG 项目：
- smoke demo 通过。
- pytest 通过。
- Agent eval 通过。
- Swagger 能稳定演示两个核心问题。
- 你能讲清楚主链路和安全边界。

回到 RAG 项目后优先做：
- 用真实文档跑一次最小问答演示。
- 检查回答是否有来源引用。
- 跑 RAG 评测集。
- 记录命中率、拒答表现和失败样例。

## 5. 最后再做融合

融合不要一开始就做。先保证 Agent 和 RAG 各自可验收，再做组合。

融合目标：
- Agent 负责结构化经营数据分析。
- RAG 负责制度、指标口径、财报说明和非结构化依据。
- 混合问题先查 SQL，再查 RAG，最后合并成“数据结论 + 文档依据”。

示例问题：

`2024 年收入增长最快的月份是哪几个？结合收入确认政策解释这些收入是否可以确认。`

理想链路：
1. Agent 用 SQL 查月度收入增速。
2. Agent 调用 RAG 查询收入确认政策。
3. 最终回答同时包含数据结论、SQL 口径、文档依据和风险提示。

## 6. 当前不要做的事

当前阶段先不要急着做：
- 大而全的前端。
- 复杂多轮规划。
- 生产级权限系统。
- SQL + RAG 深度融合。
- 大量新增业务问题。

这些事情可以作为后续优化点讲，但现在最重要的是把单项目演示闭环打稳。
